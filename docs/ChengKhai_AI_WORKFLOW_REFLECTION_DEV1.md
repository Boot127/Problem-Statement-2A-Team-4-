## C2. AI Reflection (Individual, 10 marks)

**Where AI added the most value.** The single biggest win was using Claude to *investigate before building* — twice (D1 and D2 above), the first real step wasn't writing code, it was having Claude read the existing codebase and tell me what already existed. That directly prevented two mistakes I could easily have made on my own: rebuilding a review/publish workflow that Dev 3 had already generically built, and assuming the Postgres migration was further along than it actually was (only Work Permits had it). The second biggest win was on the async migration — it's the kind of large, mechanical, easy-to-get-subtly-wrong refactor (36 files, every repository/service/controller in the app) where a human doing it by hand is genuinely more likely to miss an `await` than an AI applying the same pattern consistently across every file. What made that trustworthy wasn't the code generation itself, though — it was that Claude then verified its own work with real regression tests (including a formal 31-assertion suite) rather than asserting correctness from the diff alone. I would not have accepted "the refactor looks right" as sufficient for a change touching authentication.

**Where I rejected or significantly modified AI output.** A few concrete examples, because I think this is the part of AI-assisted work that matters most to get right:

1. **A real bug it introduced and then caught itself.** While rewriting the user repository to be Postgres-compatible, Claude initially wrote `last_login_at = NOW()` directly into a SQL query. `NOW()` is a valid Postgres function but doesn't exist in SQLite — this would have passed a syntax check and silently broken local development. It caught this itself during the same turn (before I even saw it) and rewrote it to compute the timestamp in JavaScript and bind it as a parameter instead, which is the pattern used everywhere else in the codebase. I flag this not because it's alarming that a mistake happened, but because it's a good illustration of why "the code compiles" is not the same as "the code is correct" — I made sure the regression testing phase (T1–T3) existed precisely because I don't take AI-generated SQL on faith, including SQL that Claude itself flagged as having gotten wrong once already.
2. **A near-miss deletion of working code.** When I asked for an "unused files" cleanup, Claude's first candidate was an entire directory (`client/src/features/newsletters/`) that looked orphaned by naming convention alone. Before deleting anything, it grepped for actual imports and found the directory was in active use — wrapped through thin re-export files elsewhere in the codebase — and reported this to me as a **correction of its own initial assumption** rather than proceeding. This is exactly the kind of destructive mistake that "AI output accepted without review" would produce, and it's why I explicitly scoped that cleanup request narrowly rather than letting it run wide across the whole repo unsupervised.
3. **Fabricated detail I caught in review.** When Claude drafted a contributors table for the root README, it initially invented GitHub profile URLs for each teammate's name, including guessing one for me, without actually knowing them. It caught this itself before I saw the final file and removed the invented links, replacing them with plain names — but I'm including this because it's a genuine example of an AI tool overreaching (filling in a plausible-looking detail it didn't actually have) and I want it on record that I noticed and would have rejected it myself if it hadn't self-corrected. It's a reminder that "looks complete" and "is accurate" are different things, especially for details like URLs, names, and numbers.
4. **Design decisions I made, not the AI.** Several points in this project were left as explicit judgement calls rather than the AI proceeding on its own: whether to push migration work to `origin/main` before or after a teammate's concurrent push landed, what my local `DB_PROVIDER` default should be, whether to reset test data in the shared Neon database, and how narrowly to scope a "remove unused files" request after the near-miss above. In each case Claude surfaced the decision explicitly (via clarifying questions) instead of guessing, which I consider the correct behaviour for anything touching shared team state or hard-to-reverse actions — but it also means the workflow only works well because I was actually reading and answering those questions, not rubber-stamping them.

**Overall.** My take-away is that AI was most valuable exactly where the task was large, mechanical, and verifiable (the async migration, the regression testing), and needed the most oversight exactly where it was generative and unverifiable by construction (the contributors table, any claim about "what exists" that wasn't checked against the actual code). The workflow that worked for me was: let Claude investigate and propose before building, let it build and self-verify with real tests rather than assertions, and keep the judgement calls — what to commit, what to push, what data to touch in a database other people share — explicitly mine.
